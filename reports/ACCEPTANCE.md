### 交易、規則與伺服器測試

- 256 手與修改前規則逐行動比對，合法行動、私有狀態與結果一致。
- 安全洗牌、52 張牌無重複；規則保存／恢復一致。
- 雙 session 的 HTTP/WS，非房內帳號不能讀快照或連線、設定／結果只讀本人。
- 正常 session、拒絕惡意 Origin、cookie 屬性、靜態檔白名單。
- 重複 actionId 不二次下注；同 ID 改金額拒絕；過期 handId／seq／期限拒絕。
- 100／250／500 多人 All-in 主池／邊池、未跟注退回、總籌碼守恆。
- 公開順序 0 → 3 → 4 → 5 → COMPLETE；結果不提前出現。
- 結算中故意失敗，交易 rollback，重試只提交一次；原生測試中的預期 unique violation 是拒絕重複座位的反向案例。
- 行動逾時 check/fold；斷線／只買入不連線均可在期限後退回籌碼及釋放座位。
- 事件缺號補傳、超過 256 事件範圍改回完整個人化快照。
- 原生 PostgreSQL 中在 All-in 發牌途中啟動第二個程序：舊 authority 排空後退場、新程序恢復相同 handId；結果 2 筆、結算流水 2 筆，沒有重複。
- Supabase 受控 GET user 核對普通 UUID、sub、aud、role、issuer、expiry、Email 已驗證；拒絕錯誤／過期／未驗證 token；Auth 服務故障不建立錢包；同 UUID 初始贈送僅一次。

### 真實瀏覽器的 10 項檢查

詳見 `friends-browser.json`；最終一輪擷取 **90 個 WS 封包**。

1. 兩個獨立官方 SDK 登入工作階段，伺服器 UUID 正確；把單機 localStorage 改為 999,999,999，線上錢包仍是 1,000。
2. 以 8 位碼加入兩人房，雙方只看自己的底牌。
3. 真實頁面 All-in、Flop 期間刷新、逐街公開與一次結算，總籌碼 1,000。
4. 封包中沒有 deck、seed、burn、queue、privateHoles、owners、legalByUser，未攤牌對手底牌為空。
5. 暫時斷網，再連線恢復目前伺服器序號。
6. 離桌後兩人錢包合計恢復 2,000。
7. 三個獨立頁面以 100／250／500 入桌，全押後主池 300、邊池 300，未跟注籌碼退回，整體 850 守恆。
8. 桌面截圖、390px 手機無橫向溢出、座位不與公共牌相交；登出清空記憶體與座位畫面，沒有 pageerror。
9. 故意扣住 A 的登入交換回應，再切到 B，釋放 A 回應後，畫面與伺服器 cookie 仍是 B；登出清空。
10. 原單機首頁實際載入無腳本錯誤，「真人好友房」按鈕正確開啟同源後端。

**Auth 測試的界線：** 瀏覽器真的執行隨附官方 Supabase SDK，房間真的使用 HTTP/WS 與原生 PostgreSQL，但外部 Supabase Auth 網路端點使用受控 fixture，沒有使用真實帳密、JWT、service-role 或管理員權限。不能據此宣稱現有 Supabase 專案的真實 A/B 帳號已驗證。

## 發現的問題與處理

| 問題／重現 | 處理 | 複驗 |
|---|---|---|
| Cookie 到期測試寫死 600 秒，實際經過數毫秒後為 599 秒，首次測試失敗 | 依實際 maxAge 檢查，仍限制不超過 JWT 到期 | 原生 12/12 通過 |
| 測試預期 SUM(bigint) 一定是字串，但 PGlite 回數字，首次瀏覽器測試在退桌判斷失敗 | 測試明確轉 Number 比較，伺服器存款計算不變 | PGlite／原生瀏覽器均通過 |
| 390px 手機三人牌桌，截圖發現上方座位底牌與公共牌重疊 | 手機座位固定至上方兩側與下方，公共牌置中；增加幾何相交驗證 | 手機檢查通過，截圖已更新 |
| 程式審查發現：舊帳號登入交換若被取消，伺服器仍可能完成並延遲寫 cookie | 帳號交換序列執行，舊一般請求取消；登出等待交換完成再撤銷 | 故意延遲 A、切 B 的瀏覽器測試通過 |
| 延遲登入測試最初在登出流程尚未結束時直接呼叫舊 SDK，未真的送出目標交換請求，assert(held) 失敗 | 等登出完成、目前 SDK 準備好才開始注入延遲，符合真實按鈕的可操作時機 | 最終原生瀏覽器 10/10 通過 |
| 程式審查發現：服務交接只等交易計數，未涵蓋仍在等 Auth／讀取的請求 | 停止接受新操作，追蹤在途 HTTP/WS／presence 與 timer，排空後釋放 authority | 原生雙程序 All-in 中途交接通過 |
| 正式環境誤開開發密碼登入的風險 | 設定層只允許 insecure loopback；production 明確拒絕開發旗標 | 正式 Supabase 模式拒絕本機註冊／登入；公開來源的 insecure server 拒絕 |
