# 註冊失敗調查與修復 — 2026-10-27

## 實際觀察及處理

- 使用者的首頁顯示通用「註冊失敗」，原控制台只捕捉到未展開的錯誤物件。
- 使用者自行登入 Supabase 管理台後，確認遊戲所用 midnight-poker 專案顯示 **Project is paused**。因此當時帳號服務不可用；不能把它當作帳密錯誤。
- 已恢復該既有專案，管理台先顯示 Restoration complete，之後為 **Healthy**。沒有建立另一個 Auth 專案、重置資料、變更金鑰、關閉 RLS 或關閉 Email 驗證。
- 只讀確認：Allow new users to sign up 已啟用、Email provider 已啟用、Confirm email 已啟用。
- 只讀確認：Custom SMTP 未啟用。預設測試郵件服務存在收件人及寄信額度限制；公開開放朋友使用不同信箱註冊，仍需合適的正式寄信設定。

## 程式修改

- 新增 assets/auth-feedback.js，共用根首頁及好友房的 Auth 錯誤分類。
- 服務不可用、網路失敗、信箱未驗證、密碼錯誤、弱密碼、寄信未授權、寄信限流等有不同提示。
- 控制台以可讀 JSON 輸出 operation、HTTP status、code、message、details、hint；只取需要的欄位並遮蔽 Email、token、資料庫網址、密碼形式字串。
- 官方 SDK 在 503 時可能只提供連線錯誤與 HTTP 狀態，沒有 code；忠實記錄 null，不虛構服務端代碼。
- 原單機 inline 只修改兩個指定的 Auth 提示片段；check-offline.cjs 將它們還原後比對原始 SHA，確保其他單機、AI、規則、存檔及動畫程式未被改動。

## 實際測試

`node server/tests/run-postgres.cjs --browser`：14/14 後端測試、10/10 好友房瀏覽器檢查、8/8 Auth UI 檢查，exit 0。詳見 auth-feedback-tests.log、auth-feedback-browser.json。

Auth UI 使用官方 SDK，在根首頁與好友房分別驗證 503、未授權寄信、寄信限流、註冊後要求確認信；確保密碼清空、診斷可解析且不記錄輸入帳密。沒有建立真人帳號或寄送測試信。

兩個測試 fixture 問題已修正：503 被 SDK 包裝後不保留 error code；新版 Auth API 的 code 需要正確版本及 CORS 暴露標頭。修正 fixture 後完整重跑通過。

## 仍待確認

- 使用者重新提交實際註冊後，是否成功收到驗證信並完成登入。
- 非團隊信箱的公開註冊及正式 SMTP 配置。尚未替使用者設定寄信帳密或新增外部郵件供應商。
- 真實 Supabase A/B 帳號及兩名真人對戰驗收。

參考：官方 [Auth 錯誤碼](https://supabase.com/docs/guides/auth/debugging/error-codes)、[預設 SMTP 限制](https://supabase.com/docs/guides/auth/auth-smtp)。
